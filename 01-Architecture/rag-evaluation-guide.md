# 🎯 Комплексный регламент оценки и оптимизации RAG-систем (RAG Evaluation Guide)

## 1. Введение и базовые принципы

Разработка RAG-приложения (Retrieval-Augmented Generation) не заканчивается на этапе первичной индексации документов. Критически важно проводить регулярное тестирование и калибровку всех узлов системы для поддержания точности поиска, контекстной релевантности и долгосрочной стабильности ответов.

### Три ключевых этапа пайплайна RAG:
1. **Retrieve (Извлечение):** Поиск и выборка наиболее релевантных фрагментов (чанков) информации из векторного хранилища по запросу пользователя.
2. **Augment (Обогащение контекста):** Формирование и структурирование контекстного окна для LLM с устранением смысловых пробелов, дублей и противоречий.
3. **Generate (Генерация ответа):** Формирование финального фактологически точного, безопасного и связного ответа генерирующей моделью.

| Этап пайплайна | Типичные проблемы | Последствия | Инженерные решения |
| :--- | :--- | :--- | :--- |
| **Retrieval (Поиск)** | • Низкая точность (Precision)<br>• Низкая полнота (Recall)<br>• Эффект *Lost in the Middle* | Модель получает нерелевантные фрагменты или упускает ключевые факты, находящиеся в середине длинного контекста. | • Калибровка размера чанков и оверлапа<br>• Гибридный поиск (Dense + Sparse)<br>• Кросс-энкодер Re-ranking |

## 3. Рекомендуемые фреймворки для оценки RAG

### 3.1. Ragas (Retrieval Augmented Generation Assessment)
Специализированный фреймворк для поэтапной и сквозной оценки RAG на основе тестовых датасетов (вопрос, эталонный ответ, извлеченный контекст, сгенерированный ответ).
* **Ключевые метрики:**
  * `faithfulness` — степень соответствия ответа предоставленному контексту (индикатор отсутствия галлюцинаций).
  * `answer_relevancy` — насколько сгенерированный ответ строго отвечает на заданный пользователем вопрос.
  * `context_precision` — доля релевантных чанков среди всех извлеченных документов в топе выдачи.
  * `context_recall` — способность пайплайна извлечь абсолютно все факты, необходимые для формирования эталонного ответа.
  * `context_entity_recall` — полнота извлечения ключевых сущностей (имен, терминов, артикулов).
  * `answer_similarity` — семантическое сходство сгенерированного ответа с эталоном (*ground truth*).

### 3.2. Quotient AI
Платформа для автоматизированного бенчмаркинга RAG-пайплайнов на пользовательских датасетах:
* Позволяет запускать асинхронные тесты для сравнения различных связок промптов, моделей эмбеддингов и LLM.
* Собирает детальную статистику: время отклика (`Completion Time`), лаконичность (`Completion Verbosity`, `Verbosity Ratio`), метрики сходства `ROUGE-L`, `BERTScore` и `Sentence Similarity`.
* Предоставляет Python SDK для встраивания регулярных тестов в CI/CD-пайплайны.

### 3.3. Arize Phoenix
Open-source инструмент для пошаговой трассировки, визуальной деконструкции и отладки RAG-пайплайнов:
* Обеспечивает сквозную визуализацию: `Embedding` $\to$ `Retrieval` $\to$ `Context Synthesis` $\to$ `LLM Generation`.
* Позволяет настраивать валидаторы на базе `LLM-as-a-Judge` для выявления галлюцинаций и контроля фактологии даже при отсутствии размеченного эталонного датасета (*Ground Truth-free eval*).
* Собирает телеметрию по латентности, потреблению токенов и сбоям на каждом узле системы.

## 4. Диагностика узких мест и методы оптимизации

### 4.1. Ошибки инжестинга и нарезки данных (Chunking Strategy)
* **Проблема:** Неправильный размер чанка или отсутствие перекрытия приводит к потере смыслового контекста.
* **Решения:**
  1. **Калибровка размера (Chunk Size):** Размер чанка должен соответствовать эффективному токеновому окну модели эмбеддингов.
  2. **Управление перекрытием (Chunk Overlap):** Поддерживать перекрытие в пределах 10–20% для сохранения связности между соседними блоками.
  3. **Специфичные сплиттеры:** Использовать специализированные парсеры под тип контента (`MarkdownHeaderTextSplitter` для Markdown-файлов, сплиттеры по AST для исходного кода, деление по параграфам/статьям для юридических текстов).
  4. **Визуализация:** Использовать инструменты визуализации (например, *ChunkViz*) для ручной калибровки границ разбиения.

### 4.2. Подбор модели эмбеддингов
* **Проблема:** Модель эмбеддингов не отражает смысловые связи в специализированном домене или мультиязычной среде.
* **Решения:**
  1. Ориентироваться на лидерборд **MTEB (Massive Text Embedding Benchmark)** при выборе модели под целевые языки (EN / RU / HE).
  2. Использовать оптимизированные библиотеки инференса (например, **FastEmbed**) для сокращения времени генерации векторов.
  3. Для узкопрофильных B2B-доменов обучать или дообучать (*fine-tune*) кастомные эмбеддинг-модели.

### 4.3. Оптимизация алгоритмов поиска (Retrieval)
* **Метрики качества поиска:**
  * $\text{Precision@k}$ — доля релевантных документов среди первых $k$ результатов выдачи (главный показатель точности ANN-алгоритмов).
  * $\text{MRR (Mean Reciprocal Rank)}$ — обратный ранг первого релевантного документа в результатах.
  * $\text{NDCG (Normalized Discounted Cumulative Gain)}$ — качество ранжирования с учетом градации полезности чанков.
* **Решения:**
  1. **Метрика расстояния:** Выбор оптимальной метрики схожести (Cosine Similarity, Dot Product, Euclidean Distance).
  2. **Гибридный поиск (Hybrid Search):** Объединение плотных векторов (Dense Vectors) и алгоритмов разреженного поиска по ключевым словам (Sparse Vectors: BM25, SPLADE, BM-42).
  3. **Атрибутивная фильтрация (Metadata Filtering):** Применение строгих пре-фильтров по метаданным (язык, категория, дата, теги) до выполнения векторного поиска.
  4. **Переранжирование (Re-ranking):** Внедрение Cross-Encoder моделей (например, Cohere Rerank / BGE-Reranker) для точной пересортировки топ-$N$ чанков перед отправкой в LLM.

### 4.4. Оценка качества генерации ответа LLM
* **Методы анализа:**
  * `Perplexity` — оценка предсказуемости и уверенности модели при генерации текста.
  * `ROUGE` / `BLEU` — сопоставление сгенерированного текста с эталонным переводом/саммари по n-граммам.
  * `HELM` / `EleutherAI` — бенчмаркинг устойчивости модели по различным сценариям.
  * `Diversity` — метрика разнообразия и отсутствия зацикливания формулировок.

## 5. Формирование тестовых датасетов

Для регулярного тестирования RAG-пайплайна формируется массив четверок:
$$\{ \text{question}, \text{ground\_truth}, \text{contexts}, \text{answer} \}$$

### Способы генерации данных:
1. **Ручная подготовка (Hand-crafting):** Экспертное составление пар вопрос-ответ по критическим сценариям.
2. **Синтетическая генерация (Ragas / FiddleCube):**
   * Загрузка базы знаний через Document Loaders (LangChain / LlamaIndex).
   * Автоматическая генерация разнообразных типов вопросов (простые, сравнительные, мультиязычные, рассуждающие).
   * Автоматическая фиксация исходного чанка как `ground_truth`.

## 6. Сквозная E2E-оценка (End-to-End Evaluation)

При финальной валидации продакшен-системы замеряются 5 ключевых параметров:

```text
[ Пользовательский запрос ] ──► [ RAG Pipeline ] ──► [ Финальный ответ ]
                                                            │
    ┌───────────────────────┬───────────────────────┬───────┴───────────────┬───────────────────────┐
    ▼                       ▼                       ▼                       ▼                       ▼
Helpfulness            Groundedness             Latency                 Conciseness             Consistency
(Полезность ответа)   (Приземленность к фактам)  (Латентность < 1.5s)   (Лаконичность)          (Воспроизводимость)

```

1. **Groundedness (Обоснованность):** Ответ строго опирается на найденные документы без выдуманных фактов.
2. **Helpfulness (Полезность):** Ответ полно и практично закрывает потребность пользователя.
3. **Latency (Латентность):** Суммарное время ответа (векторизация + поиск + реранкинг + генерация).
4. **Conciseness (Лаконичность):** Отсутствие лишнего шума и соответствие заданному формату.
5. **Consistency (Стабильность):** Одинаково высокое качество ответов на схожие по смыслу формулировки.

## 7. Чек-лист внедрения оценки в архитектуру проекта

* [ ] Настроить логирование запросов, контекстов и ответов в базу данных (PostgreSQL / pgvector / Phoenix).
* [ ] Сформировать эталонный валидационный датасет (от 50 до 100 контрольных вопросов).
* [ ] Интегрировать автоматический запуск тестов Ragas в CI/CD пайплайн (GitHub Actions).
* [ ] Установить целевые пороги метрик: `Faithfulness >= 0.85`, `Context Precision >= 0.80`.
* [ ] Внедрить связку Hybrid Search (Dense + BM25) и шаг Re-ranking для минимизации галлюцинаций.
