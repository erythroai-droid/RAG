# Targo — производственный план

Версия: 2026-10-03. Основа: план «Erythro NeoBabylon» от пользователя, сведённый с `docs/context/CHECKLIST.md`, `docs/whatsapp-tech-provider.md` и `docs/compliance/whatsapp-data-privacy.md`. Очередь действий — `docs/context/CHECKLIST.md`. Здесь решения и этапы.

Targo — языковой помощник для бизнеса: одно приложение оператора, в которое функции перевода добавляются по очереди (см. «Развитие продукта»). Первая функция — общение с клиентами в WhatsApp с переводом на русский и обратно. Основной рынок — Израиль. До 2026-10-04 продукт назывался B2Bridge. Боевой мост WhatsApp ↔ Telegram на `wa.erythro.ai` — его прототип и первый «клиент» (демо-номер Erythro).

## Режим работы сейчас (решение пользователя 2026-10-03)

Продажа не начинается, пока Meta не подтвердит верификацию бизнеса Erythro, не выдаст статус Tech Provider и не одобрит проверку приложения. Сейчас Targo тестирует только пользователь на демо-номере Erythro. В работу идут Этапы 0–4 и переход демо. **Отложено до подтверждения Meta и до первой продажи:** Этап 5 (онбординг, триал, состояния `trial`/`blocked`/`active`), лендинг, клиентские поддомены `*.targo`, переопределение вебхука и его проверка на тестовом аккаунте, письменные условия и договор, документы «до первой продажи». Решения по этим пунктам ниже остаются в силе и применяются, когда продажа станет возможной.

## Рамки Meta (регламент)

1. **Возможности терминала определяет Cloud API Meta.** Правила первого контакта, 24-часовое окно, форматы кнопок и звонки заданы текущей спецификацией. Переписка вне 24-часового окна возможна только одобренным шаблоном (Template Message).
2. **Версии.** Следим за релизами Graph API и политиками. Версия API задаётся настройкой, а не зашита в код. Сейчас в `core/whatsapp_gateway.py` зашито `v20.0` в четырёх местах.
3. **Обновления.** Фронтенд-PWA обновляется на устройствах через Service Worker. Серверная часть (Docker на VPS) обновляется деплоем, который делается только по явной просьбе пользователя. В договоре не обещать «мгновенно».
4. **Чужой номер подключается только** после верификации бизнеса Erythro, статуса Tech Provider и проверки приложения (`docs/whatsapp-tech-provider.md`).

## Архитектура

```
Meta Cloud API ──► wa.erythro.ai ──► Caddy ──► ядро (Python/FastAPI) ──► app.db (SQLite)
                                                   ▲                         │
                                                   │ внутренняя сеть Docker   │ единственный писатель
                                         Next.js (PWA оператора) ◄────────────┘
                                         + SSE/Web Push оператору

Инженерный контур (отдельный сервис Erythro): тикеты, support_master.db, Magic Link
```

- В каждой установке: контейнер ядра, контейнер Next.js, свой `.env`, свой том с `app.db`, свой пароль. Токены Telegram клиенту не задаются.
- Порт на хост не публикуется. Наружу только Caddy.
- Токен Meta клиента лежит в `.env` его копии, не в общей базе.
- Редис и BullMQ не нужны, пока процесс один: очередь и лимиты держит сам процесс ядра.

**Доставка вебхука (решение 2026-10-03).** У приложения Meta один общий адрес вебхука, но его можно переопределить для аккаунта WhatsApp или для номера клиента: `POST /<WABA_ID>/subscribed_apps` либо `POST /<PHONE_NUMBER_ID>` с параметрами `override_callback_uri` и `verify_token` (источник: документация Meta, раздел Webhook overrides). При онбординге клиента его номер получает адрес `https://wa.erythro.ai/t/<client>/webhook/whatsapp`, и Caddy направляет этот путь в контейнер копии клиента. Центральной очереди и общей точки отказа нет.
- Адрес приложения `https://wa.erythro.ai/webhook/whatsapp` остаётся: туда Meta всегда шлёт вебхуки шаблонов и уровня аккаунта (они не переопределяются), и там работает демо-номер Erythro.
- Каждая копия принимает только события со своим `phone_number_id` и проверяет подпись Meta.
- Не подтверждено документацией: подписывается ли переопределённый вебхук тем же секретом приложения. Проверка ждёт Tech Provider и проверку приложения, пробный запуск на тестовом аккаунте WhatsApp `854956307641254`. Если проверка не пройдёт, запасной вариант — маленький шлюз по `phone_number_id`: разбор всех `entry` и `changes`, подпись по необработанному телу, очередь на диске с повторной отправкой, без n8n.

## Этап 0. Гигиена боевого моста (до PWA, малые правки Python)

- [ ] Проверка подписи Meta `X-Hub-Signature-256` на `/webhook/whatsapp` до перевода. Сейчас подписи нет, и поддельное сообщение уйдёт в Gemini и Telegram.
- [ ] Версия Graph API параметром `GRAPH_API_VERSION`, проверить актуальную.
- [ ] Поле `last_webhook_at` в `/health` и оповещение через n8n, если вебхуков нет несколько часов в рабочее время (инцидент 2026-10-02, PIT-102).

## Этап 1. Ядро и SQLite

- Файл `app.db` на томе установки. Режим при открытии: `journal_mode=WAL`, `synchronous=NORMAL`, плюс `busy_timeout` и `foreign_keys=ON`. Доступ к базе только из Python.
- Идентификатор клиента в базе с первой строки. Миграции файлами SQL.
- Таблицы: контакты, диалоги, сообщения (оригинал, русский текст, то, что ушло в WhatsApp, статус), вложения, настройки установки, состояние лицензии.
- Вебхук: подпись Meta, защита от повтора одного сообщения, определение клиента по `phone_number_id` из тела запроса.
- Лимиты и очередь в памяти процесса: 20–30 запросов в минуту к Gemini на установку, не больше двух одновременно. На один номер: 20 сообщений в минуту в перевод, 20 вложений в час, 30 ответов оператора в минуту. Длина входящего текста для перевода режется до 2 000–3 000 символов. Фото до 5 МБ, файл до 20 МБ.
- Ключ Gemini: проверить условия платного уровня или Vertex до подключения чужих переписок (письменные условия обработки Google в чеклисте «до договора»).
- Кнопки прямого звонка `tel:+…` в интерфейсе и CTA автоответа.
- `sessions.json` остаётся связкой «карточка Telegram → клиент» до перехода (см. «Переход демо»).

## Этап 2. Клиентский терминал оператора (PWA)

- Next.js 15, React 19, Tailwind 4, по макету `pwa/design/mockup.html` и токенам из `pwa/static/tokens.css`.
- Экраны: вход, список диалогов, диалог (оригинал и перевод, предпросмотр перед отправкой), поле ответа, баннеры состояний. Языки приложения: RU, EN, HE, AR (иврит и арабский с зеркалированием; арабский добавлен решением пользователя 2026-10-04).
- Контакты: «+ Новый диалог» (формат E.164, по умолчанию `+972`, имя, язык HE/EN/RU/AR) создаёт контакт. Ответ клиенту возможен только внутри 24-часового окна. Когда окна нет, интерфейс показывает баннер «только шаблон» (шаблоны в бэклоге).
- Входящее от неизвестного номера: контакт со статусом «Новый клиент», мгновенный перевод и Web Push оператору.
- PWA: манифест с брендом Targo, `sw.js`, запрет кэша для `sw.js` в Caddy, обновление с предложением «Обновить» (не принудительный `skipWaiting` посреди работы). Web Push с VAPID. На iPhone пуши работают только у PWA, добавленной на экран «Домой» (iOS 16.4+).
- Вход: пароль (хэш), восстановление по одноразовой ссылке.
- Языковые пакеты (решения пользователя 2026-10-04):
  - Начальный пакет — одна пара языков, её выбирают при покупке (например, русский оператора и иврит клиентов). Язык оператора задан покупкой, при установке не выбирается и потом не меняется.
  - Пакеты дороже содержат больше языков. В них при установке PWA предлагает выбрать язык оператора; по умолчанию выбран язык системы устройства первого входа (`navigator.languages`, первый из языков пакета; если ни одного нет, английский). Другие устройства его не переопределяют. Потом язык оператора можно менять в настройках PWA.
  - Язык оператора — это язык интерфейса PWA и язык, на который переводятся входящие.
  - Приветствие при первом сообщении уходит на языке клиентов из пары, не на языке оператора.
  - Сообщение на языке вне пакета: оригинал без перевода с пометкой «Язык вне пакета». Ответ без перевода возможен через `!!`.
  - Пакет хранится в состоянии лицензии и проверяется ядром, не только интерфейсом.
  - Сейчас ядро переводит только на русский оператора; для другого языка оператора промпты нужно сделать зависимыми от пары.
  - Пакет с несколькими языками клиентов: пока продажи только в Израиле, приветствие на иврите, если собеседник ещё ничего не написал по существу. При выходе на другие рынки правило поменяется; возможно, язык по умолчанию будет зависеть от субдомена рынка (не решено).

## Этап 3. Инженерный контур

- Отдельный сервис Erythro на адресе `tech.erythro.ai` (запись A на `46.202.155.56`, DNS only, создаёт пользователь). Вход по роли `engineer`, устанавливается на телефон пользователя. Адрес не под `*.targo`, поэтому имя не пересекается с именами клиентов.
- Тикеты: форма поддержки в клиентском PWA → тикет `#TICK-XXXX` в `support_master.db` → папка в инженерном PWA в реальном времени (SSE). Переписка по тикету с обеих сторон, push и звук, кнопка звонка клиенту. Копии установок передают тикет по HTTPS с ключом установки. В тикет попадает то, что написал клиент в форме, но не переписка с его покупателями.
- Таблица `support_incidents` с флагом `analyzedByAi: false` для будущего анализа.

## Этап 4. Диагностика, приватность, бэкапы

- **Magic Link для инженера.** Инженер создаёт временную ссылку из папки тикета (15–30 минут). Токен не лежит в строке адреса: в ссылке одноразовый код, он обменивается на cookie. Клиент подтверждает доступ кнопкой, каждое действие пишется в журнал, из диагностики вырезаются тексты сообщений и номера. Доступ: консоль ошибок, статус Service Worker, состояние вебхука, сброс кэша.
- **Приватность** (`docs/compliance/whatsapp-data-privacy.md`): уведомление в приветствии, выгрузка и удаление переписки одного номера по просьбе клиента.
- **Бэкапы на хосте.** Ночная копия `sqlite3 app.db ".backup …"`, шифрование ключом `BACKUP_ENCRYPTION_KEY`, который не лежит рядом с файлами. Хранится несколько последних, в каталоге вне тома установки. Раз в месяц проверка восстановления.
  - Ограничение: копия лежит на той же машине, что и рабочий файл. От порчи и удаления она защищает, от потери самого VPS нет. Недельный снимок Hostinger возвращает на одну дату все установки сразу. Внешняя копия — в бэклоге.

## Этап 5. Онбординг и жизненный цикл установки (отложен до подтверждения Meta)

- Создание установки: каталог, `.env`, пустой `app.db` с миграциями, пароль, ссылка на первый вход. Автоматизация через n8n, но n8n не получает пароль root VPS: нужен узкий механизм (например, ключ SSH с одной разрешённой командой).
- Состояния установки хранятся в её базе и проверяются ядром:
  - `trial`: 72 часа от активации, до 150–200 сообщений. Идёт на тестовом номере Meta (решение 2026-10-03). По моим сведениям, тестовый номер принимает и пишет только на заранее подтверждённых получателей (до 5 номеров), поэтому триал это песочница: заявитель добавляет свой телефон в список и пишет с него. Несколько триалов одновременно на одном тестовом номере различить по `phone_number_id` нельзя, значит триалы идут по очереди. Проверить по документации Meta до реализации;
  - `blocked`: срок или лимит вышел, PWA показывает платёжный экран, ответы оператора не отправляются;
  - `active`: тариф оплачен.
- **`blocked` (решено 2026-10-03):** входящие принимаются и хранятся не более 30 дней, затем ночное задание их удаляет (из копий по мере их смены). Только текст и служебные поля: вложения не скачиваются, хранится идентификатор медиа (Meta держит файл до 30 дней), перевод не выполняется, автоответ клиенту не отправляется. Объём в `blocked` ограничен (число сообщений в сутки и размер базы, значения определить при реализации); сверх лимита новые входящие отбрасываются с записью в журнал. После оплаты в пределах 30 дней оператор видит накопленное, перевод выполняется при открытии диалога.
- До включения триала заявитель принимает условия обработки данных (согласие нажатием), иначе у Erythro нет основания хранить его переписку.

## Переход демо

Демо-номер Erythro работает через PWA и ту же ленту. Проверка с чужого телефона: текст, ответ, режим «как написано», фото и файл. Только после этого Telegram на демо выключается. Meta шлёт все события приложения на один адрес вебхука, поэтому Python-ядро с Telegram и новое ядро одновременно один вебхук не слушают.

## Развитие продукта (решение пользователя 2026-10-04)

Targo — одно приложение, отдельных продуктов и линейки нет. Функции добавляются в него по очереди:

1. Перевод переписки в WhatsApp (сейчас, Этапы 0–5).
2. Перевод звонков.
3. Перевод документов.
4. Дальше по мере развития.

Сроки и устройство пунктов 2–4 не решены. Название и интерфейс не привязывать к чату: в бренде и манифесте только «Targo».

## Бэклог (после первого релиза)

- Первое сообщение тому, кто не писал, и сообщения после закрытия окна: одобренные шаблоны на каждый язык, согласие получателя, оплата Meta, лимит 250 новых номеров в сутки, перевод переменных через Gemini.
- Несколько клиентов в одном процессе с отдельным Postgres. Подключение номера с сайта (Embedded Signup v4).
- Внешняя копия бэкапов (S3-совместимое хранилище, с добавлением получателя в документ о данных).
- **Модуль A. Автономный анализ инцидентов.** Расписание в n8n, выборка `support_incidents` с `analyzedByAi=false`, кластеризация причин Gemini, карточки задач через GitHub API (`bug`, `ai-backlog`, критерии приёмки), проставление `analyzedByAi=true`. Перед отправкой в Gemini и GitHub тексты очищаются от номеров и переписки.
- **Модуль B. Enterprise: закрытый периметр (Private APN).** Серверная часть без публичных адресов, доступ только изнутри частной точки доступа оператора связи, туннели IPsec/GRE или Zero Trust, ИИ через частные эндпоинты (Vertex AI Private Service Connect). Ограничения: вебхуки Meta должны достучаться из интернета, значит нужен публичный входной ретранслятор; привязку к IMSI/IMEI браузерное приложение не читает, реалистичнее mTLS с сертификатами устройств.
